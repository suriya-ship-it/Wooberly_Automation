# Release Notes - v1.6 (Unified Multi-Stage E2E Automation Orchestration: test:step #1)

## Overview
Release **v1.6** introduces the unified end-to-end automation command `npm run "test:step #1"` (alongside shortcuts `test:step1` and `test:step-1`). It seamlessly orchestrates the entire cross-application flow between the Driver app (`com.radicalstart.wooberlydriver`) and the Rider app (`com.radicalstart.wooberly`), coordinating Stage 1 (Driver Online), Stage 2 (Rider Booking & Dispatch), and Stage 3 (Driver Acceptance & Full 13-Step Trip Lifecycle) with zero manual intervention.

## What's New

### 1. Unified Step #1 Orchestrator (`npm run "test:step #1"`)
- Implemented in [`tests/e2e/wooberly_step1_flow.ts`](file:///Users/radicalstart/Documents/appium-automation/tests/e2e/wooberly_step1_flow.ts) and configured in [`package.json`](file:///Users/radicalstart/Documents/appium-automation/package.json).
- Sequentially executes:
  - **Stage 1 (`npm run test:driver-online`)**: Launches Driver app, handles system permissions, bypasses authentication if already logged in, and toggles driver to "You're online".
  - **Stage 2 (`npm run test:login`)**: Launches Rider app, authenticates via phone + OTP, searches destination ("Mattuthavani madurai"), selects ride category, confirms cash payment, and dispatches the booking request.
  - **Stage 3 (`npm run test:trip`)**: Explicitly brings Driver app into the foreground, catches incoming ride request modal, accepts the trip, and completes the entire 13-step ride lifecycle.

### 2. Standalone & Modular Trip Flow (`tests/e2e/wooberly_trip_flow.ts`)
- Standalone execution script `npm run test:trip` allowing targeted execution of Stage 3 independently or through the orchestrator.
- Includes automatic foregrounding with dual-layer intents (`adb shell monkey` + `am start` + `driver.activateApp`).
- Low-latency selector polling (`waitForIdleTimeout: 100`, `waitForSelectorTimeout: 500`) eliminating UiAutomator2 polling stalls and ensuring the 30-second ride request modal is accepted within seconds.

### 3. Full 13-Step In-Ride & Post-Trip Lifecycle
1. **Step 1**: Driver swipes "Location reached" slider (`y = 1713`).
2. **Step 2**: Driver expands bottom sheet (Up Arrow) and opens in-ride Chat.
3. **Step 3**: Driver types message, closes keyboard cleanly, and clicks Send button.
4. **Step 4**: Driver clicks Back `<` button from chat, and collapses bottom sheet handle.
5. **Step 5**: Driver swipes "Start ride" slider, dynamically fetches Rider 4-digit OTP via Android logcat, enters OTP, and verifies.
6. **Step 6**: Driver swipes "Complete ride" slider.
7. **Step 7**: Driver enters `$1` in Toll Charges field, clicks "Done", and navigates through Driver Trip Details via "Next ->".
8. **Step 8**: Driver holds Cash Confirmation modal ("Did you collect cash?") in background.
9. **Step 9**: Switches foreground to Rider app.
10. **Step 10**: Rider clicks "Confirm ->" button on trip details.
11. **Step 11**: Rider submits 5-star rating on Review screen and clicks "Done ->".
12. **Step 12**: Switches back to Driver app and clicks "Yes ->" on Cash Confirmation modal.
13. **Step 13**: Driver submits 5-star rating on Review screen and clicks "Done ->" to return to online home screen.

## Issues Resolved & Stability Enhancements

- **UiAutomator2 Timeout Optimization**: Default 10–20s element wait times caused incoming ride request modals to expire before the accept button could be clicked. Configured settings to 500ms timeouts and prioritized the `Accept` selector check first.
- **Reliable Foreground Activity Switching**: Fixed issues where `activateApp` alone failed to bring Flutter activity to the visual foreground by pairing it with ADB launcher intents.
- **Toll Page Dismissal Fix**: Replaced blind Android back keyevents with `driver.hideKeyboard()` and explicit `description("Done")` button targeting to prevent cancelling the Toll modal.
- **OTP Input Separation**: Fixed issue where OTP was erroneously typed into the phone number field by ensuring strict page settlement before typing.
